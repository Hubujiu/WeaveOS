Implementation facts and complexity:

- AccessForWrite retains the seven existing DB statements and trusted account/
  source locks. Caller acquires query revisions first, then account/dependencies,
  application FOR UPDATE, catalog registration. No permission cache was added.
- Read methods use one short RR transaction for active account, app/catalog,
  actual menu ownership, groups/members/grants and returned policy revision.
- List performs 2+3A data statements for A stored apps, then linear evaluation of
  joined member/grant rows. It has no pagination in this frozen contract. This
  deliberate finite implementation has an N+1 round-trip cost; no scale benchmark
  is claimed. Request metadata/control statements are excluded from this count.
- Member/grant normalization deduplicates and sorts: O(M log M)/O(G log G), with
  O(M)/O(G) storage validation/inserts and one full replacement. The existing 1MiB
  HTTP limit bounds each submitted payload. All writes preserve PR21 revision
  locking, so cross-domain writes can serialize at the existing revision locks.
- Every policy write stores a SHA256 route/kind/normalized-DTO fingerprint and
  only result/status/Location. Unique actor/key, config, minimal safe audit and
  result share one transaction; unknown COMMIT is never retried by the server.
- No operation-retention cleanup job is frozen; the operation table can grow.
  No fields registry/data HTTP grants, owner transfer, delegate/delete API,
  member search, dynamic tables or Flowable was introduced.
